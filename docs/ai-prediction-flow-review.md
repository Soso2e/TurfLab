## 現行の実行記録

- Windows Workerは `gpt-6.1-sol`（low）、補助はAntigravity `agy` の `gemini-4-hydrogen-medium`。11/22の日付のジョブは自由予想7件がCodex（約111～242秒）、不足補完6件・外部根拠収集3件もCodex、公式結果6件・翌日レビュー3件はHydrogenだった。根拠はローカルの各CLI `receipt.json`。ジョブの正常応答とCoreでの正式確定は個別に確認する。
- `callBucket` が `-context-v*` だけを予想枠とし、既定の `-free-v2` は調査枠を消費する。CLI選択は別の処理で、未列挙のジョブが「固定入力から1レースを分析」扱いになるため、自由予想・不足補完・外部根拠収集がまとめてCodexに送られる。公式結果とレビューは同じ日次枠（10回）。
- 11/23早朝のWorkerは `healthy` でも、主催区分の公式照合待ちが7件。Coreの11/22～23の日次出力は6レース、正式確定予想・公式結果とも0件だった。一方、11/22のローカルLabには自由予想7件があり、数値予測の状態欄はいずれも未記録。対象台帳の範囲が異なるため、個々のLab・Core・結果・精算はレースIDで突き合わせる必要がある。
- 同じChatGPTログインで、PATH先頭のCodex CLI 0.165.0は `gpt-6.2-sol` を拒否し、デスクトップ版に同梱されたCLI 0.171.0-alpha.13は成功した。同梱版のディレクトリを検証プロセス内だけでPATH先頭に置き、既存の `predictWithCodex` から構造化JSONを取得。receiptは `provider: codex`、`model: gpt-6.2-sol`、`exit_code: 0`。実データを使わない疎通確認で、固定pack・定期起動での受入が残る。

## 工程ごとの担当

| 工程 | 担当と出力 |
| --- | --- |
| 公式出馬表、個体・主催区分の照合、近走・騎手成績の取得、馬場・天候、限定的な欠測補完、外部記事の出典抽出 | 既存CSV・Core・公式取得処理を先に使う。AI検索が必要な箇所はHydrogen。情報項目、出典、取得時刻、欠測理由を構造化して返す。 |
| 複数資料間の矛盾、全頭の複雑な補完、公式照合の難しい例外 | 必要なときだけSOL 6.2。突合理由と根拠候補を返し、公式ID・日付・競馬場・レース番号・全頭をCore側で確認できる場合に採用する。 |
| 発走前予想、全頭評価・3展開・印・独立した数値予測 | SOL 6.2。検証済みの固定packと発走前観測を使う。欠測・根拠不足は暫定として記録し、正式化は既存Coreの検証と読み返しで判断する。 |
| 発走前の取消・馬場・オッズ更新、仮想Bet | 事実確認は既存の取得処理とHydrogen。確率・印の固定後に時点付きオッズを使用し、EV・金額・締切・取消再計算は既存計算とCoreが担当。AIの印・参考買い目の予算と本人Betは既存の区分を維持する。 |
| 公式着順・払戻・返還の取得と精算 | 公式取得処理、必要箇所はHydrogen。完全性・訂正・仮想精算はCoreで処理する。 |
| 予想と実走の差、ラップ・通過順の比較、改善仮説 | SOL 6.2。確定した事実、仮説、検証案を出力する。既存の時系列検証と再現確認を経て戦略ルールへ反映する。 |

## 変更方針と受入

### 公式データの取込

- 構造化された事実はTypeScriptで取り込み、出典と観測時刻を付けてCoreで検証する。過去走は保存済みの成績と取り込んだNAR公式CSVから先に埋め、不足項目だけを調査に回す。予想には検証済みの固定packを渡す。
- 地方競馬の公式出馬表には馬の登録コード付きリンクと直近5走の欄があり、掲載されている各走の成績表へのリンクを使える。2026-11-26の名古屋9Rで確認した。NARの定期収集は本人保存の公式ZIP/CSV取込を使う。出馬表・成績表・ダウンロードの動的URLはNARの robots.txt の自動巡回対象外。CSVで足りない項目は、保存済みの成績表URLと当時の馬番を不足補完に渡す。保存した公式ページを取込元にする場合は、馬の登録コードと開催日・場・R・当時の馬番の照合を受入条件とする。[公式出馬表](https://www.keiba.go.jp/KeibaWeb/TodayRaceInfo/DebaTable?k_babaCode=24&k_raceDate=2026%2F11%2F26&k_raceNo=9) · [robots.txt](https://www.keiba.go.jp/robots.txt)
- 中央競馬はJRA-VANのJV-LinkをWindows側の取得元候補とし、利用条件と必要項目の配信を確認できた段階でTypeScriptの取込へつなぐ。[JRA-VAN公式SDK](https://developer.jra-van.jp/t/topic/45)

1. **ジョブ種別を明示する。** ジョブ作成時に種別を渡し、モデル・検索可否・呼出し枠・表示名を同じ定義から決める。予想、軽検索、公式結果取得、レビューをそれぞれ追跡し、レビュー集中時にも結果取得・精算が進むようにする。既存ジョブIDと保存済み応答は再利用し、発走後の再実行による上書きや二重処理を防ぐ。既存の「Hydrogen失敗→固定6.1→Claude」と「Codex失敗→Claude」は工程ごとの明示設定へ見直し、設定モデル・実行モデル・失敗・代替実行をreceiptに記録する。
2. **工程別のプロンプト契約を整理する。** 共通ルールは出典・情報締切・欠測・JSON契約。予想は固定された根拠を渡してWeb検索を無効化し、補完が必要なときは収集工程へ戻す。現状は独立数値予測に外部印禁止を指示する一方、同じ入力に外部印を渡し、戦略ルールにもリアルタイムオッズ参照がある。まず市場情報・外部印が入らない入力で予想を凍結し、外部根拠との照合とオッズによる期待値評価は凍結後に行う。独立性は入力項目と時点の検査で担保する。正式昇格も全頭6評価の充足に加え、根拠ID・時点・対象レースとの一致を確認する。
3. **振り返りを本番プロンプトから切り離す。** 現状はレビューの仮説をGit管理下の `prompts/ai-strategy-rules.md` に自動追記し、次の自由予想に即時投入する。本番には版管理された採用ルールを読み込ませ、レビュー候補は既存レビュー記録に保持する。実際に送ったプロンプト版・入力ハッシュ・出典時点・設定/実行モデルを保存し、数値予測にも設定モデルではなく実行receiptを反映する。呼出し成功、Lab保存、Core正式化、公式結果、精算、レビューを別の状態として表示する。
4. **朝9時タスクとの責任分担をそろえる。** 朝タスクは候補・参考レポート・根拠不足の表示を担当し、正式予想の生成主体をローカルSOLへ寄せる。既存の手動ChatGPT取込と保存済み予想は維持する。同一レースとpackに対する自動の二重生成・二重採用を防ぐ。実タスクの設定は実装時に確認し、リポジトリ内の本文更新と実タスクの変更を個別に扱う。
5. **最初の実装単位は振り分け・枠・receipt。** 現行モデルのまま全ジョブ種別、再起動、既存キャッシュ、呼出し枠、モデル拒否を検証。その後に工程別プロンプトと振り返り候補の分離を行う。WindowsのWorker起動時にSOL 6.2対応CLIを明示選択し、実行ファイルと版を記録する。更新で変わるWindowsAppsの版付きパスは固定しない。隔離した固定packで必要なJSON・全頭評価・数値予測と定期起動時の実行ファイル選択を確認してから切り替える。実開催1Rで出典→pack→適切なCLI→発走前凍結→Core読み返し→公式結果・仮想精算→翌日レビューを確認する。JRA/NAR両方の取得を今後の受入対象とする。
